Your AI coding agent runs the install. This page holds the instructions it follows, so you don't need to read them yourself.

1. Check the prerequisites and decide your inputs in [Get Started on AWS](/self-hosting/full/aws/overview).
2. Copy the instructions below with the copy button.
3. Paste them into your agent along with the prompt from Get Started, then stay available for the steps that need a person.

<Note>
  The instructions mention companion runbooks (Validation, Upgrade, REST API, SAML and SCIM, Backup and Restore) that are not published on this site yet. Ask Velt for them.
</Note>

````markdown Agent instructions (AWS) expandable
**Outcome:** the Velt portable backend running entirely inside the customer's own AWS account — GovCloud

1. **Substrate** — an EKS cluster (Kubernetes Secrets encrypted with your KMS key; Bottlerocket FIPS nodes on

   any OIDC provider).
4. **SDK** — the Velt client SDK bundle served from the same host, so your pages download nothing from Velt.
5. **A first workspace** — an API key, an organization and an admin user seeded into the deployment's own database.

## To the agent executing this — read this first

- **Execute phases in order.** Each phase ends with a **Verify** block; do not continue until it passes.
- **Maintain the state file** (`velt-selfhost-aws-state.json`, below) after every step. A fresh session resumes
  from this guide plus the state file — never from memory.
- **One account, one partition.** GovCloud and the commercial partition are different accounts with different
  credentials; never run a step against an account other than `$ACCOUNT_ID`. Every resource is prefixed by
  `DEPLOYMENT_NAME`; never touch anything outside it.
- **The partition is asserted, never assumed.** The module refuses a plan whose credentials or region disagree with
  `partition`. If you see that refusal you are signed in to the wrong account — do not "fix" it by changing the
  variable.
- **All versions come from the release** (Phase 0). The images, the chart, the Terraform module and the tools bundle
  are one release. Never substitute a different version for one component.
- **Verify before you use.** Every artifact — manifest, tools, module, each image, the chart — is verified with
  `cosign` against Velt's release identity before anything is extracted, copied or installed. A verification failure is
  a **stop**, never a retry.
- **Human moments are known in advance** — show the operator the table in *Inputs* before starting.
- **Long waits are normal (expected):** the EKS cluster ~10–15 min, RDS ~15–25 min (longer with Multi-AZ), the node
  group ~5 min, the first ALB ~3 min. Say so when a long wait starts.
- **Never print a secret.** The ES256 private key, the RDS master password, the DSNs and the workspace auth token go
  into the operator's secret store; the state file and your report carry **paths, names and ARNs**, never values.
- If a command fails, check **Troubleshooting** at the end before escalating.

### Features you can turn on — decide now or later

Every optional feature is off until it is turned on, and every one can be turned on after the install with a
`helm upgrade` plus whatever outside piece it needs. Decide on purpose rather than inherit the defaults; the how-to for
each is under "After the install → Turning a feature on later".

**This guide can be newer than your release.** The two rows marked *(after 0.1.17)* need a release newer than 0.1.17;
on 0.1.17 or older, skip their steps — the Cluster Autoscaler half of 4.1, the alarm steps of 1.2, 1.5 and Phase 5,
their lines in the final report and the idle steps — and leave their variables out of the tfvars (1.2 checks it).

| Feature | Default | Asked above as | Outside the chart it needs |
|---|---|---|---|
| REST API (server-to-server) | off | `rest-api` in `enabledModules` (Phase 4.2) | nothing — the API key's auth token from Phase 3.1, seeded in Phase 4.7 |
| Comment attachments | off | `ATTACHMENT_ORIGINS` | the application role's bucket grants and the bucket's CORS rule (Terraform `enable_storage_grants`, `attachment_cors_origins`); the bucket itself is always created |
| Advanced webhooks | off | Webhook V2 delivery | `direct`: nothing; `svix`: a Secret with the customer's Svix token |
| Console SAML sign-in + SCIM | off | Console SAML sign-in + SCIM | a SAML app in the customer's identity provider |
| Self-hosted SDK bundle | off in the chart; this guide's values turn it on | `sdk:` block (Phase 4.2) | the `velt-sdk-static` image copied into ECR (Phase 2.1); the app's `cdnHost` pin (Phase 7) |
| Webhook payload encryption | off | — (decide later) | a Secret holding the encryption key |
| Deployment-wide token minting | off, and off is the safe choice | — (decide later) | a Secret holding the master token; only for internal services that mint tokens across several API keys |
| Private comments | per API key | Private comments? | nothing — the console (or the seed's `--project-config`) |
| Email notifications | per API key, off | — (decide later) | the customer's own SendGrid or Customer.io account, set on the API key in the console |
| Permission provider | per API key, off | — (decide later) | an HTTPS endpoint of the customer's that answers Velt's permission questions, reachable from the cluster, set on the API key in the console |
| FIPS mode (nodes and application) | on in GovCloud, off in the commercial partition | `fips_enabled` (Phase 1.2) and `fips.enabled` (Phase 4.2) | **an install-time choice**: changing `fips_enabled` changes the node group's image type, which replaces the nodes (expected); the application's `fips.enabled` follows it |
| FIPS service endpoints | off | — (decide later) | Terraform `aws_use_fips_endpoints`: the module's own AWS calls, and the S3 and STS endpoints it hands the chart for attachments, use each service's FIPS endpoint (expected) |
| Node autoscaling *(after 0.1.17)* | on: the node group starts at `node_count` and may grow to `node_max_count` (twice `node_count` unless set) | — (Phase 1.2) | the Cluster Autoscaler, installed with Helm in Phase 4.1 under the IAM role the module creates; vCPU quota for the ceiling (Phase 0.4) |
| Alarms *(after 0.1.17)* | on in `persistent`, off in `sandbox` | Alarm recipients | a subscription to the alarm topic (email addresses in Phase 1.2, or your own topic); the certificate alarm takes its ARN, and the load balancer's alarms appear, on one more apply after Phase 5. ### 0.1 Resolve and VERIFY the release manifest

The umbrella manifest is the trust root. Its `tierB` block pins every portable artifact by digest; the AWS module is
`tierB.modules.aws`. The release registry is read anonymously — no login. If `oras` or `cosign` answers `error getting
credentials`, your Docker configuration sends this registry to a credential helper (the gcloud one, typically) that
fails for anonymous reads: export an empty configuration, and keep it exported for the rest of the install — Phase
2.1's two ECR logins then land in the same configuration, which the copies into ECR and the provision CLI read. A
fresh session exports it again and logs in again. **Record your Docker engine first:** the configuration also holds
the docker CLI's context, and on Colima or Docker Desktop an empty one makes `docker` fall back to
`/var/run/docker.sock`, which does not exist there (`failed to connect to the docker API`) — and 2.1's `docker login`
and 3.1's provision CLI both need Docker:

```bash
export DOCKER_HOST=$(docker context inspect --format '{{.Endpoints.docker.Host}}')   # BEFORE the next line
export DOCKER_CONFIG=$(mktemp -d)
```

```bash
# Resolve the tag ONCE to its digest, verify that digest, then pull that digest:
MANIFEST_DIGEST=$(oras manifest fetch --descriptor "$REG/velt-selfhost-manifest:latest" \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['digest'])")
# The manifest is published by a different workflow than the images, so its identity differs:
cosign verify --certificate-identity-regexp '^https://github\.com/snippyly/shared-firebase-function/\.github/workflows/selfhost-umbrella-publish\.yml@refs/heads/main$' \
  --certificate-oidc-issuer "$ISSUER" "$REG/velt-selfhost-manifest@$MANIFEST_DIGEST" \
  && oras pull -o . "$REG/velt-selfhost-manifest@$MANIFEST_DIGEST"    # writes manifest.json
python3 -c "import json;m=json.load(open('manifest.json'));t=m.get('tierB') or {};print(t.get('portableVersion'), 'aws module pinned' if (t.get('modules') or {}).get('aws') else 'NO aws module pin')"
```

**Verify and fetch by one digest.** The registry is asked what a tag names every time a command uses the tag, so a
verification by tag followed by a pull by tag gets two answers, and only the first was checked. Every step below that
pulls or copies an artifact from the release registry resolves the tag once (`oras manifest fetch --descriptor`),
verifies that digest, and pulls or copies that same digest. Do not put the tag back in place of the digest.

When the manifest pins `PORTABLE_V` and carries `modules.aws`, record `manifestVerified: true`. When it pins no AWS
module, take `PORTABLE_V` from the newest release that published `velt-portable-module-aws` and record
`manifestVerified: false` — every artifact below is still verified individually. Filter to released versions: cosign
keeps its signature tags (`sha256-….sig`) in the same repository, and they sort above every version.

```bash
oras repo tags "$REG/velt-portable-module-aws" | grep -E '^[0-9]+\.[0-9]+\.[0-9]+$' | sort -V | tail -1
```

The console and the SDK move on their own versions; read them from the verified manifest. A manifest may omit either
one — every manifest published before the release pipeline began pinning the SDK omits `sdkStatic`. Then take the
newest version a portable release published, the same rule the release pipeline uses to pin it. Only Velt's release job
builds and signs these images, so 2.1 still verifies them against the same signer as everything else. Record in the
report which one came from the registry rather than the manifest:

```bash
CONSOLE_V=$(python3 -c "import json;r=(json.load(open('manifest.json')).get('tierB') or {}).get('images',{}).get('consoleStatic');print(r['ref'].rsplit(':',1)[1] if r else '')")
SDK_V=$(python3 -c "import json;r=(json.load(open('manifest.json')).get('tierB') or {}).get('images',{}).get('sdkStatic');print(r['ref'].rsplit(':',1)[1] if r else '')")
echo "manifest: console=${CONSOLE_V:-absent} sdk=${SDK_V:-absent}"
[[ -n "$CONSOLE_V" ]] || CONSOLE_V=$(oras repo tags "$REG/velt-console-static" | grep -E '^[0-9]+\.[0-9]+\.[0-9]+$' | sort -V | tail -1)
[[ -n "$SDK_V" ]] || SDK_V=$(oras repo tags "$REG/velt-sdk-static" | grep -E '^[0-9]+\.[0-9]+\.[0-9]+$' | sort -V | tail -1)
echo "using:    console=${CONSOLE_V:-absent} sdk=${SDK_V:-absent}"
```

If either is still `absent`, no release has published that image: skip it in 2.1 and set its `enabled: false` in 4.2.

### 0.3 Sign in to AWS (human moment 1)

The operator signs in to the account and partition the deployment goes into — through IAM Identity Center
(`aws sso login --profile <profile>`), or the customer's federation. GovCloud has its own identity system and its own
profile. Then:

```bash
export AWS_PROFILE=<profile> AWS_REGION=<REGION>
aws sts get-caller-identity          # the Account must be $ACCOUNT_ID; the Arn's partition must be $PARTITION
```

The role must be an administrator for the install (the preflight simulates every action the module needs).

**Credentials that last through the apply.** Phase 1.3 runs for half an hour or more, and Terraform refreshes the
session itself. With an `aws login` or IAM Identity Center (SSO) profile that refresh can fail part-way —
`failed to refresh cached credentials … CreateOAuth2Token … The provided authorization grant is invalid` — while the
AWS CLI refreshes the same session without trouble. Hand Terraform a profile that asks the CLI for credentials
instead, and use it for the rest of the install:

```ini
# ~/.aws/config — next to your sign-in profile
[profile <profile>-cli]
credential_process = aws configure export-credentials --profile <profile> --format process
region = <REGION>
```

```bash
export AWS_PROFILE=<profile>-cli
aws sts get-caller-identity          # the same Account and Arn as above
```

The sign-in session itself must still outlast the install: sign in again before Phase 1.3 if it is close to expiring.

**Organization policies.** An account in an AWS Organization may be bound by service control policies. Three shapes
matter here, and the preflight names each one it meets:

| Policy shape | What breaks without care | What to do |
|---|---|---|
| a **region allow-list** | an apply in another region dies part-way | pick an allowed region and set `allowed_regions` in the tfvars (1.2): a plan anywhere else is refused before anything is created. Nothing in the module needs `us-east-1` |
| **IAM OIDC-provider actions denied** (`iam:*OpenIDConnectProvider*`) | the module creates the cluster's OIDC provider, which IAM roles for service accounts trust: the apply would create the cluster and then fail | ask the management account to allow it for this account, or use the two-step apply (1.4) |
| a **spend cap** on the member account | the install may stop when the cap is reached | ask the management account what the cap is |

### 0.4 Quotas (human moment 2)

The node group needs `nodes × vCPUs` On-Demand standard vCPUs at rest. The Cluster Autoscaler may grow it to
`node_max_count` nodes (twice `node_count` unless set), and a managed node group's version update first adds up to
twice its availability-zone count in nodes on top of whatever size it has then (expected). With the module's defaults:

| mode | nodes | at rest | at the autoscaler's ceiling | at the ceiling, during a node-group update |
|---|---|---|---|---|
| `sandbox` | 2 × `m6i.large` (2 vCPU) over 2 zones, ceiling 4 | 4 | 8 | 16 |
| `persistent` | 3 × `m6i.xlarge` (4 vCPU) over 3 zones, ceiling 6 | 12 | 24 | 48 |

Plus one Elastic IP per NAT gateway (sandbox 1, persistent one per zone) and one VPC. The preflight refuses below the
at-rest figure and warns below the last figure, naming the value to request; pass `--max-nodes` if you set
`node_max_count`. To request it:

```bash
aws service-quotas get-service-quota --service-code ec2 --quota-code L-1216C47A --region "$AWS_REGION"
aws service-quotas request-service-quota-increase --service-code ec2 --quota-code L-1216C47A \
  --desired-value <the value the preflight names> --region "$AWS_REGION"
```

A small increase is often approved automatically within minutes (observed: 32 → 48 vCPUs). Re-run the `get` above,
or the preflight, before waiting on it.

### 0.5 Run the install preflight

```bash
./velt-portable-tools/portable-install-preflight-aws.sh --partition "$PARTITION" --region "$REGION" \
  --account-id "$ACCOUNT_ID" --mode "$MODE" --kubernetes-version "$K8S_VERSION" --fips \
  --ecr-prefix "$DEPLOYMENT_NAME/" --manifest-ref "$REG/velt-selfhost-manifest:latest" \
  --portable-version "$PORTABLE_V" --manifest-file ./manifest.json --report ./preflight-report.json
# Commercial partition: drop --fips unless you want FIPS nodes there too. Under an organization policy that denies
# the OIDC-provider actions, add --without-eks-oidc-provider and follow 1.4.
```

`--manifest-ref` takes the tag, as written: P9 resolves it, verifies that digest itself and checks that
`./manifest.json` is the manifest that verified. If `latest` has moved since 0.1 it refuses — repeat 0.1, then run
the preflight again.

It **creates nothing** — every fact it needs has a read API. It stops at the first failure and has no flag to skip
one. Exit 0 = pass (a `WARN` line passes: read it and log it); 1 = a check failed and the report names it; 2 = usage.

| Check | What it proves |
|---|---|
| P1 | `aws` ≥ 2.15, `terraform` ≥ 1.6, `helm` ≥ 3.17 (the chart is installed by its digest), `node` ≥ 18, a `python3` that runs, `kubectl`, `cosign`, `oras` on the PATH |
| P2 | the session is on `--account-id`, in `--partition`, and the region is in that partition |
| P10 | no organization policy denies the IAM OIDC-provider actions (or you chose the two-step apply) |
| P3 | the deploying role may perform every action the module needs |
| P4 | the region offers the zones and the `vpc-cni`, `aws-ebs-csi-driver` and `metrics-server` add-ons at the version |
| P5 | RDS for PostgreSQL 16 is orderable as the instance class in the region |
| P6 | the node type is x86_64 and offered in enough zones; with `--fips`, the Bottlerocket FIPS image exists for the version |
| P7 | the vCPU and Elastic IP quotas leave room (0.4) |
| P8 | the module's seven ECR repositories either all exist or none do |
| P9 | the manifest verifies, and its `tierB` pin is not newer than `PORTABLE_V` |
| P11 | the budgets the account can read (never a refusal) |

### 0.6 The console's identity provider (human moment 3)

Terraform writes the console's runtime config from the issuer and client id (1.2), so the provider must exist first.
Any OIDC provider your organization runs works if it meets the same rules; with **Amazon Cognito**:

```bash
# 1. The user pool: members sign in with their email, the email is verified automatically, only an administrator
#    creates users, and a changed email must be verified again. The password policy is an example — use yours.
POOL=$(aws cognito-idp create-user-pool --pool-name "$DEPLOYMENT_NAME-console" \
  --username-attributes email --auto-verified-attributes email \
  --admin-create-user-config AllowAdminCreateUserOnly=true \
  --policies 'PasswordPolicy={MinimumLength=12,RequireUppercase=true,RequireLowercase=true,RequireNumbers=true,RequireSymbols=false}' \
  --user-attribute-update-settings AttributesRequireVerificationBeforeUpdate=email \
  --query UserPool.Id --output text); echo "pool $POOL"

# 2. A domain for the hosted sign-in page. REQUIRED: without one the discovery document has no
#    authorization_endpoint, and the console has nowhere to send the user.
aws cognito-idp create-user-pool-domain --user-pool-id "$POOL" --domain "$DEPLOYMENT_NAME-console-$ACCOUNT_ID" >/dev/null \
  && echo "domain $DEPLOYMENT_NAME-console-$ACCOUNT_ID"

# 3. The public app client: no secret (the console runs PKCE), the authorization-code grant, openid/email/profile,
#    callback /signup. Users may write only `name` — never email or preferred_username.
CONSOLE_AUTH_CLIENT_ID=$(aws cognito-idp create-user-pool-client --user-pool-id "$POOL" --client-name "$DEPLOYMENT_NAME-console" \
  --no-generate-secret --allowed-o-auth-flows code --allowed-o-auth-scopes openid email profile \
  --allowed-o-auth-flows-user-pool-client --supported-identity-providers COGNITO \
  --callback-urls "https://$PUBLIC_HOST/signup" --logout-urls "https://$PUBLIC_HOST/" "https://$PUBLIC_HOST/signup" \
  --read-attributes email email_verified name preferred_username \
  --write-attributes name \
  --explicit-auth-flows ALLOW_REFRESH_TOKEN_AUTH ALLOW_USER_SRP_AUTH \
  --query UserPoolClient.ClientId --output text); echo "client $CONSOLE_AUTH_CLIENT_ID"

# 4. Measure the issuer (Cognito's has no trailing slash) and check the domain is live.
CONSOLE_AUTH_ISSUER=$(curl -s "https://cognito-idp.$REGION.amazonaws.com/$POOL/.well-known/openid-configuration" | jq -r .issuer)
echo "issuer [$CONSOLE_AUTH_ISSUER]"     # use exactly this as console_auth_issuer (1.2) and consoleAuth.oidcIssuer (4.2)
curl -s "https://cognito-idp.$REGION.amazonaws.com/$POOL/.well-known/openid-configuration" | jq '{authorization_endpoint,end_session_endpoint}'   # both set

# 5. The console admin as a Cognito user — the same email as --console-admin-email (4.7). No invitation email, the
#    email marked verified, a permanent password kept in Secrets Manager and never printed.
PW="Vt$(openssl rand -hex 10)Q9"
aws cognito-idp admin-create-user --user-pool-id "$POOL" --username "$CONSOLE_ADMIN_EMAIL" \
  --user-attributes Name=email,Value="$CONSOLE_ADMIN_EMAIL" Name=email_verified,Value=true --message-action SUPPRESS \
  --query User.UserStatus --output text
aws cognito-idp admin-set-user-password --user-pool-id "$POOL" --username "$CONSOLE_ADMIN_EMAIL" --password "$PW" --permanent
aws secretsmanager create-secret --name "$DEPLOYMENT_NAME/console-admin-password" --secret-string "$PW" --query Name --output text
unset PW
```

Why the rules: console members are matched by email, so a user who could write their own `email` (or
`preferred_username`) could impersonate a member — the client lets users write only `name`, and the pool verifies
email. The issuer must match **character for character**. A token that carries `email_verified` is refused unless the
claim is `true` (or the string `"true"`); a token without the claim is accepted. Record the pool id
(`inputs.consoleAuthUserPoolId`): the pool is not in Terraform, and the teardown deletes it.

**Verify (phase gate):** the preflight exited 0; `artifacts.preflightReport` is recorded; the issuer and client id are
in the state file. Mark `0-release: done`.

### 2.1 Verify, then copy by digest

```bash

for PAIR in "velt-console-static:$CONSOLE_V" "velt-sdk-static:$SDK_V"; do

### 2.2 Vulnerability scan + sign-off (human moment 5)

ECR scans each image on push: `aws ecr describe-image-scan-findings --repository-name "$DEPLOYMENT_NAME/velt-gateway"
--image-id imageTag="$PORTABLE_V"` (and the others). If that answers `ScanNotFoundException` on a tag, the tag names an
image index (a multi-platform image, or one built with attestations) rather than one image: read the findings by the
`linux/amd64` manifest's digest (`docker manifest inspect "$ECR/velt-gateway:<tag>"` lists it) with
`--image-id imageDigest=<that digest>`. Persistent-mode repositories refuse to move a tag (re-copying the same release
is expected to be accepted for cosign's own signature tags).

Velt's release fails on any critical or high finding that has a fix. Findings with **no fix** in the base image's
Debian release can still appear: on 0.1.17, each of gateway, workers and migrate showed seven HIGH findings in
util-linux and zlib that Debian 12 has not fixed, and upstream Valkey carries its own. So the sign-off compares the
list with the [Debian security tracker](https://security-tracker.debian.org/tracker/) rather than expecting zero. List
the critical and high findings with their packages (basic scanning; with Amazon Inspector's enhanced scanning the
findings are under `enhancedFindings` instead):

```bash
for IMG in velt-gateway velt-workers velt-migrate velt-console-static velt-sdk-static valkey; do
  TAG=$PORTABLE_V; [ "$IMG" = velt-console-static ] && TAG=$CONSOLE_V; [ "$IMG" = velt-sdk-static ] && TAG=$SDK_V; [ "$IMG" = valkey ] && TAG=8
  aws ecr describe-image-scan-findings --repository-name "$DEPLOYMENT_NAME/$IMG" --image-id imageTag="$TAG" --region "$REGION" \
    --query 'imageScanFindings.findings[?severity==`CRITICAL` || severity==`HIGH`].[severity,name,attributes[?key==`package_name`].value|[0]]' \
    --output text | sed "s|^|$IMG  |"
done
```

This step is your security team's sign-off.

**Verify (phase gate):** every image and the chart are in ECR under `PORTABLE_V` (or their own versions), each
verified before the copy; the scan is signed off. Mark `2-images: done`.

### 3.3 The database credentials

The migrate Job logs in as the RDS administrator and creates a least-privilege application role on its first run; the
gateway and workers log in as that role. The administrator password is managed by RDS in Secrets Manager and may
contain URL-special characters, so it is percent-encoded:

```bash
PG_HOST=$(tfo rds_endpoint)
ADMIN_PW=$(aws secretsmanager get-secret-value --secret-id "$(tfo rds_master_secret_arn)" --query SecretString --output text \
  | python3 -c 'import json,sys,urllib.parse;print(urllib.parse.quote(json.load(sys.stdin)["password"],safe=""))')
APP_PW=$(openssl rand -base64 24 | tr -d '/+=')
# ONE command, so an empty value stops it before any secret is written: a secret with an empty host or password is
# accepted here and only fails much later, at the migrate hook, with nothing pointing back to this step.
[ -n "$PG_HOST" ] && [ -n "$ADMIN_PW" ] && [ -n "$APP_PW" ] \
  && kubectl -n velt create secret generic velt-postgres-dsn-admin \
       --from-literal=VELT_PG_DSN="postgres://veltadmin:${ADMIN_PW}@${PG_HOST}:5432/velt?sslmode=verify-full" \
  && kubectl -n velt create secret generic velt-app-db --from-literal=VELT_APP_DB_PASSWORD="${APP_PW}" \
  && kubectl -n velt create secret generic velt-postgres-dsn \
       --from-literal=VELT_PG_DSN="postgres://velt_app:${APP_PW}@${PG_HOST}:5432/velt?sslmode=verify-full" \
  || echo "STOP: a value is empty or a secret was not created — fix it before going on"
unset ADMIN_PW APP_PW
```

RDS rotates the administrator password. Only the migrate Job reads `velt-postgres-dsn-admin`, and it runs on every
upgrade — the Upgrade Guide's AWS section rebuilds it from Secrets Manager first.

### 3.4 The encrypted storage class for the cache

### 3.5 The certificate for `PUBLIC_HOST` (human moment 6)

The load balancer controller does not read Kubernetes TLS secrets: the certificate comes from ACM, and the values file
names it (4.2). Request it here, before the install. Until it is `ISSUED` the controller creates the load balancer
and its `:80` listener but not `:443` (its log repeats `CreateListener … 400`), and the Ingress shows no address. Its
DNS validation needs the zone's owner and can take a while, so start it now:

```bash
ACM_CERT_ARN=$(aws acm request-certificate --domain-name "$PUBLIC_HOST" --validation-method DNS --region "$REGION" \
  --query CertificateArn --output text)
# the validation record the zone's owner creates (empty for a few seconds after the request — run it again)
aws acm describe-certificate --certificate-arn "$ACM_CERT_ARN" --region "$REGION" \
  --query 'Certificate.DomainValidationOptions[0].ResourceRecord'
aws acm wait certificate-validated --certificate-arn "$ACM_CERT_ARN" --region "$REGION"   # returns once ISSUED
echo "$ACM_CERT_ARN"   # 4.2's certificate-arn
```

Or import yours (`aws acm import-certificate`, for a private certificate authority or an air-gapped network). The
certificate must be in the load balancer's region, `$REGION`. No access to the DNS zone yet: Phase 5's test path
installs without a certificate and adds one afterwards.

**An imported certificate never renews by itself.** ACM renews a certificate it issued, automatically, for as long as
its validation record stays in the zone (keep that record); an imported one simply expires, and the load balancer
then serves an expired certificate to every client. Phase 5 points the certificate alarm at it so the expiry reaches
you 30 days ahead; renew by importing the replacement into the SAME ARN, which the load balancer picks up without a
change: `aws acm import-certificate --certificate-arn "$ACM_CERT_ARN" --certificate fileb://cert.pem --private-key
fileb://key.pem --certificate-chain fileb://chain.pem --region "$REGION"`.

```bash

helm search repo autoscaler/cluster-autoscaler --versions | head   # pick the chart whose APP VERSION has K8S_VERSION's minor
helm install cluster-autoscaler autoscaler/cluster-autoscaler -n kube-system --version <that chart version> \
  --set fullnameOverride=cluster-autoscaler --set cloudProvider=aws --set awsRegion="$REGION" \

  --set rbac.serviceAccount.create=true --set rbac.serviceAccount.name=cluster-autoscaler \
  --set rbac.serviceAccount.annotations."eks\.amazonaws\.com/role-arn"="$(tfo cluster_autoscaler_role_arn)" \
  --set extraArgs.skip-nodes-with-local-storage=false

```

The autoscaler's minor version must match the cluster's (an autoscaler for 1.33 on a 1.33 cluster): after an EKS
version upgrade, upgrade it to the matching chart. The ServiceAccount must be `kube-system/cluster-autoscaler` — the
module's role trusts exactly that one — and the role can resize only the Auto Scaling groups, in this region, that EKS
tagged as this cluster's. `skip-nodes-with-local-storage=false` is required: every Velt pod mounts a scratch volume
for `/tmp`, and with the autoscaler's default no node running a Velt pod is ever removed, so the group only grows.
It never removes the node running the cache pod (Valkey): the chart marks that pod `safe-to-evict: "false"`, because
every gateway is unready while it moves (its volume detaches and re-attaches, then the cache reloads — minutes). Other
nodes it drains wait for the chart's disruption budgets. A node failure or a node-group upgrade still moves the cache
pod. By default the autoscaler also keeps a node that runs a `kube-system` pod with no disruption budget (the load
balancer controller, metrics-server): if the group stays above `node_count` long after load drops, that is why — give
those Deployments a PodDisruptionBudget, or install with `--set extraArgs.skip-nodes-with-system-pods=false`.

### 4.7 Seed the first workspace (in-cluster)

The database is private, so the provision CLI runs inside the cluster from the migrate image, with the gateway's own
DSN secret and the RDS certificate. It is idempotent: re-running upserts, never duplicates.

Two credentials come out of this step, for two different ladders of the REST API — do not confuse them:

- the **API key's auth token** (`x-velt-api-key` + `x-velt-auth-token`): what the REST API document calls "that
  apiKey's auth token", and what the console shows as the API key's **Auth Token**. You chose it in Phase 3.1
  (`<api-auth-token>`); the seed stores it hashed;
- the **workspace auth token** (`x-velt-workspace-id` + `x-velt-workspace-auth-token`): the deployment-scoped
  credential of the `/v2/workspace/*` family. The seed GENERATES it and prints it once — the console shows it as
  **Workspace Auth Token**.

A request on one ladder with the other ladder's token is refused with `403 Invalid Auth token.`.

```bash
# Inline JSON for --project-config and --identify-config is fine: neither carries a secret. The inner quotes are
# backslash-escaped because each value is spliced into the --overrides JSON string below.
PRIVATE_COMMENTS='{\"isPrivateCommentsEnabled\":true}'     # or '{}' when the customer does not use private comments
# The identify configuration needs BOTH flags — a config without them is refused:
#   requireAutoOrgUser  true:  a user who identifies into an organization is added to it (the hosted default for a new
#                              API key); false: add users to organizations through the REST API first
#   requireJwtToken     false: identify accepts a user without a token from your server (the hosted default); true: only
#                              users your server signs (needs your verification key as customerJwt)
IDENTIFY_CONFIG='{\"allowedOrigins\":[\"<app-origin>\"],\"requireAutoOrgUser\":true,\"requireJwtToken\":false}'  # APP_ORIGINS — every browser origin of the app, comma separated inside the array
API_AUTH_TOKEN=$(aws secretsmanager get-secret-value --secret-id "$DEPLOYMENT_NAME/api-auth-token" --query SecretString --output text)
kubectl -n velt run velt-provision --restart=Never --image="$ECR/velt-migrate:$PORTABLE_V" \
  --overrides='{"spec":{"volumes":[{"name":"ca","configMap":{"name":"velt-postgres-ca"}}],"containers":[{"name":"velt-provision",
    "image":"'"$ECR/velt-migrate:$PORTABLE_V"'","envFrom":[{"secretRef":{"name":"velt-postgres-dsn"}}],
    "env":[{"name":"NODE_EXTRA_CA_CERTS","value":"/ca/ca.pem"}],"volumeMounts":[{"name":"ca","mountPath":"/ca"}],
    "command":["node","dist/portable-runtime/src/provision-cli.js","seed",
      "--api-key","<api-key>","--org-id","<org-id>","--user-id-hash","<admin-user-id-hash>",
      "--console-admin-email","<console-admin-email>",
      "--allowed-domains","<allowed-domains>",
      "--identify-config","'"$IDENTIFY_CONFIG"'",
      "--auth-token","'"$API_AUTH_TOKEN"'",
      "--project-config","'"$PRIVATE_COMMENTS"'"]}]}}'
# The log holds the generated WORKSPACE auth token (one bare line, printed once) next to a node `pg` SSL-mode
# warning: capture it straight into Secrets Manager, then delete the pod so the log is gone. ONE command: a failed seed,
# or a line that is not a token, stores nothing and keeps the pod so you can read its log.
kubectl -n velt wait pod/velt-provision --for=jsonpath='{.status.phase}'=Succeeded --timeout=120s \
  && ( umask 077; kubectl -n velt logs velt-provision | grep -vE '^\[|warning|Warning' | tail -1 > seed-workspace-token.txt ) \
  && grep -qE '^[A-Za-z0-9_-]{32,}$' seed-workspace-token.txt \
  && aws secretsmanager create-secret --name "$DEPLOYMENT_NAME/workspace-auth-token" --secret-string file://seed-workspace-token.txt >/dev/null \
  && kubectl -n velt delete pod velt-provision \
  || echo "NOT stored — read: kubectl -n velt logs velt-provision; fix, then kubectl -n velt delete pod velt-provision"
rm -f seed-workspace-token.txt; unset API_AUTH_TOKEN
```

The pod runs detached and is read from its log on purpose: an attached run can lose the output, and a re-seed never
prints the workspace token again (it is stored hashed). If the log shows `workspace auth token already provisioned`,
the first run's token is the one in Secrets Manager; re-seeding is otherwise idempotent (that run prints `NOT stored`,
which is expected there — delete the pod).

`--allowed-domains` is required — identify refuses a workspace with none; `--console-admin-email` is who can sign in
to the console. **`--identify-config` matters beyond CORS:** a workspace seeded without one has no identify
configuration, and adding a second workspace in the console then fails with `cannot create a second live apiKey …
until every existing apiKey has a valid identify config` until the first has one (Troubleshooting).

**Verify (phase gate):** `helm -n velt status velt-portable` is `deployed`; the migrate pod is `Completed`; the schema
head matches the chart; the seed completed and the token is stored; every pod is `Running` and Ready. Mark
`4-helm: done`.

initVelt('<api-key>', {
  // BUNDLE axis — where the JavaScript is downloaded FROM. Omit either line and the loader goes to cdn.velt.dev,
  // even with strict: true (the two axes are independent).
  version: '<SDK_V>',                                  // MUST equal sdk.version in values-aws.yaml
  proxyConfig: { cdnHost: 'https://<PUBLIC_HOST>' },   // serves /lib/sdk@<SDK_V>/…
  // RUNTIME axis — where the SDK TALKS to.
  selfHosted: {
    enablePortableBackend: true,
    portableBackendUrl: 'https://<PUBLIC_HOST>/api',   // the /api base — the SDK appends /identify to it
    strict: true,                                      // without it the SDK still calls Velt hosts
  },
})
```

Four silent traps on the bundle axis:

- **`version` defaults to the wrapper's own built-in version**, not `latest`. Pin it, equal to `sdk.version`, or the
  path 404s.
- **`staging: true` / `develop: true` beat the pin** — both point at a Velt host. Never set them on a self-hosted page.
- **The whole directory is served, not one file.** `velt.js` imports dozens of sibling chunks relative to its own path;
  the `velt-sdk-static` image carries all of them, and Phase 6's two `/lib/sdk@…` checks prove they are served.
- **One image serves one version.** When you later move `sdk.version`, keep the old one in `sdk.retainedVersions`
  until every app has repointed (the Upgrade Guide's Phase U5).

### 7.2 The checks

1. **Console sign-in.** Open `https://<PUBLIC_HOST>` and sign in as the console admin: the email passed to
   `--console-admin-email` in 4.7, which is the Cognito user of 0.6 (its password is in Secrets Manager,
   `$DEPLOYMENT_NAME/console-admin-password`). After the redirect back from Cognito the console waits on `/signup`
   with a spinner for 10–15 seconds before the dashboard (observed) — wait; do not reload.
2. **SDK loop.** Open the app with the 7.1 config. In the browser's network log, filtered on `velt`: the bundle loads
   from **your** host; `window.Velt.version` equals `SDK_V`; a new comment renders, and its calls go to
   `https://<PUBLIC_HOST>/api` and `wss://<PUBLIC_HOST>/ws`.
3. **Cross-surface proof.** The comment from step 2 is visible in the console. The console's Data view lists
   organizations and documents by their **server ids**, not the ids your app uses; compute them to find the right rows:

   ```bash
   # the organization's server id (MD5 of the organization id)
   node -e 'console.log(require("crypto").createHash("md5").update(process.argv[1]).digest("hex"))' "$ORG_ID"
   # the document's server id (cyrb53 of the document id)
   node -e 'const s=process.argv[1];let h1=0xdeadbeef,h2=0x41c6ce57;for(let i=0;i<s.length;i++){const c=s.charCodeAt(i);h1=Math.imul(h1^c,2654435761);h2=Math.imul(h2^c,1597334677)}h1=Math.imul(h1^(h1>>>16),2246822507)^Math.imul(h2^(h2>>>13),3266489909);h2=Math.imul(h2^(h2>>>16),2246822507)^Math.imul(h1^(h1>>>13),3266489909);console.log(4294967296*(2097151&h2)+(h1>>>0))' "<the document id the app set>"
   ```

   The comment detail pane shows the annotation id, not the text or author — match on the id the SDK shows for the
   comment. The console session lives in the operator's browser; when you (the agent) must verify this alone and the
   REST API is on, read the comment through it instead — the same proof from the other door:

   ```bash
   API_AUTH_TOKEN=$(aws secretsmanager get-secret-value --secret-id "$DEPLOYMENT_NAME/api-auth-token" --query SecretString --output text)
   curl -sS "https://$PUBLIC_HOST/api/v2/commentannotations/get" -H 'content-type: application/json' \
     -H "x-velt-api-key: $API_KEY" -H "x-velt-auth-token: $API_AUTH_TOKEN" \
     -d "{\"data\":{\"organizationId\":\"$ORG_ID\",\"documentId\":\"<the document id the app set>\"}}" | jq '.result.data | length'   # ≥ 1
   unset API_AUTH_TOKEN
   ```

4. **Zero-egress audit.** Across both sessions the network log contains **no request to any Velt-owned host** — no
   `cdn.velt.dev`, `api.velt.dev`, `staging.velt.dev`, no Velt analytics. `strict: true` silences the SDK's runtime
   calls; only `proxyConfig.cdnHost` decides where the bundle comes from, a choice made before `velt.js` exists. A page
   without the pin passes checks 1–3 and fails this one on its very first request: set both, or state plainly in the
   report that the deployment is backend-sealed and CDN-dependent.
5. **With attachments on:** attach a file to a comment in the app, reload, open it. The upload and the download go to
   **your** bucket (`<bucket>.s3.<region>.amazonaws.com`, or its FIPS endpoint) and the signed-URL requests to your
   host — nothing to a Velt host.

**Driving the checks with a browser automation tool** (observed in a 0.1.17 run):

- The SDK's elements render in shadow DOM: `document.querySelectorAll` finds nothing inside them. Use your tool's
  locators that pierce shadow roots.
- Enter does not submit the comment composer; click `button[aria-label="Save new comment"]`.
- On a bare stand-in page, open the comments sidebar by clicking `velt-sidebar-button`; `openCommentSidebar()` did not
  open it there.
- An attachment's download button appears only on hover.
- The console's "Sign in with your organization" is neither a button nor a link: select it by its text, not its role.
- Record every request's host from a fresh browser context: that list is check 4's evidence.

**Verify (final gate):** checks 1–4 pass (and 5 with attachments on). Mark `7-acceptance: done`.

## After the install

### What this costs to run, and how to idle it

A persistent deployment is three general-purpose EKS nodes, an RDS instance (Multi-AZ in persistent mode), NAT
gateways, an ALB, KMS keys, ECR and an S3 bucket; read the figures for your sizes from the AWS pricing calculator —
the nodes, RDS and the NAT gateways dominate; the Cluster Autoscaler adds nodes (up to `node_max_count`) only while
pods need them. Between evaluation windows, stop the autoscaler first (it would otherwise add nodes back for the
pending pods), then scale the node group to zero, and stop RDS (AWS restarts a stopped RDS instance after 7 days —
stop it again for a longer window). The NAT gateways and the ALB keep billing while idle.

```bash
kubectl -n kube-system scale deploy/cluster-autoscaler --replicas=0
aws eks update-nodegroup-config --cluster-name "$(tfo eks_cluster_name)" --nodegroup-name "$(tfo eks_node_group_name)" \
  --scaling-config minSize=0,maxSize=<node_max_count>,desiredSize=0 --region "$REGION"
# to resume: minSize=<node_count>,desiredSize=<node_count>, then scale the autoscaler back to 1 replica
```

Resume BEFORE any `terraform apply`: Terraform no longer sets the group's size, so an apply while it is idled sends
the minimum `node_count` beside a size of 0, and EKS refuses it (`Minimum capacity … can't be greater than desired
size`). In persistent mode the RDS alarms report the stopped instance as missing data, not as an alarm.

### Teardown

Uninstall the application first, then delete its namespace, then destroy:

```bash
helm uninstall velt-portable -n velt --wait   # removes the Ingress; the controller deletes the ALB (not in Terraform's state; it holds the public subnets)
kubectl delete namespace velt --wait          # the cache's volume: its claim outlives helm uninstall, and its EBS volume is not in Terraform's state
aws ec2 describe-volumes --region "$REGION" --filters Name=status,Values=available \
  --query 'Volumes[].[VolumeId,Tags[?Key==`kubernetes.io/created-for/pvc/namespace`]|[0].Value]' --output text   # nothing left for velt
helm uninstall aws-load-balancer-controller -n kube-system
terraform -chdir=terraform/aws destroy
```

**The cache's volume.** A StatefulSet's volume claim is not removed by `helm uninstall`, and the EBS volume behind
it is the CSI driver's, not Terraform's — skip the namespace step and it is left behind, billing. Deleting the
namespace removes the claim and the driver deletes the volume. The namespace takes several minutes to go (about ten
measured: the workers' termination grace period); that is not a hang. In persistent mode deletion protection is on:
destroy refuses until it is turned off deliberately —
`aws rds modify-db-instance --db-instance-identifier <DEPLOYMENT_NAME>-pg --no-deletion-protection --apply-immediately`,
which is the step that lets the database be deleted (it leaves the final snapshot below). The KMS keys enter a pending-deletion window rather than disappearing at once; their aliases
and the two log groups are deleted with them, so a reinstall under the same `DEPLOYMENT_NAME` does not collide.

Two things the destroy does not remove, and that matter for a reinstall under the same name:

- **The Cognito user pool** (0.6) is not in Terraform: delete its domain, then the pool —
  `aws cognito-idp delete-user-pool-domain --user-pool-id <pool id> --domain "$DEPLOYMENT_NAME-console-$ACCOUNT_ID"`,
  then `aws cognito-idp delete-user-pool --user-pool-id <pool id>` (the id is `inputs.consoleAuthUserPoolId`).
- **The Secrets Manager secrets** you created (`$DEPLOYMENT_NAME/…`, Phases 0.6, 3 and 4.7) are not in Terraform. Delete
  them — `aws secretsmanager delete-secret --secret-id "$DEPLOYMENT_NAME/<name>" --force-delete-without-recovery` — or
  keep them for the reinstall. Deleted WITH a recovery window, a name stays reserved for that window and the reinstall's
  `create-secret` refuses it; `aws secretsmanager restore-secret` brings it back.
- **The final database snapshot** (persistent mode), `<DEPLOYMENT_NAME>-pg-final`, is your data: it stays until you
  delete it. A later persistent destroy under the same name needs that name free, so delete or copy it first. **It is
  encrypted with the module's RDS key, and the destroy schedules that key for deletion** (30 days in persistent mode):
  once the key is gone the snapshot cannot be restored. To keep it, copy it under a key you keep, or cancel the key's
  deletion inside the window — the Backup and Restore runbook has both
  commands.

**Keep the DNS zone.** If `PUBLIC_HOST` lives in a Route 53 hosted zone, delete only the records this install added (the
certificate's validation record and the record for `PUBLIC_HOST`), never the zone itself: a new zone gets new name
servers, and the domain stops resolving until its registration — or the parent zone's delegation — is pointed at them.

### Alarms, and what they do not cover

In persistent mode every alarm notifies the alarm topic (`alarm_topic_arn`), once when it fires and once when it
clears, and each alarm's description says what to look at:

| Alarm | Fires when | First look |
|---|---|---|
| `<DEPLOYMENT_NAME>-rds-cpu` | RDS averages above 80% CPU for 15 minutes | long-running queries, then a larger `rds_instance_class` |
| `<DEPLOYMENT_NAME>-rds-free-storage` | free storage stays below 10% of `rds_allocated_storage_gb` for half an hour | storage autoscaling has hit its cap (4 × `rds_allocated_storage_gb`) or cannot keep up: raise `rds_allocated_storage_gb` and apply |
| `<DEPLOYMENT_NAME>-node-cpu` | the nodes average above 80% CPU for 15 minutes | is the node group at `node_max_count`? raise it or the instance size |
| `<DEPLOYMENT_NAME>-node-memory` | the nodes' memory averages above 85% for 15 minutes (Container Insights) | `kubectl top nodes` and the Redis pod's memory — the cache must fit on one node; raise `node_max_count` or the instance size |
| `<DEPLOYMENT_NAME>-certificate-expiry` | the certificate expires in under 30 days | import the replacement into the same ARN, or check the renewal's validation record |
| `<DEPLOYMENT_NAME>-alb-5xx` | the load balancer answers more than 10 requests in five minutes with its own 5xx (503: no healthy gateway pod) | the gateway pods and the target groups' health |
| `<DEPLOYMENT_NAME>-gateway-5xx` | the Velt pods answer more than 10 requests per five minutes with a 5xx, for 15 minutes | the gateway's logs. Its 501 for an endpoint this deployment does not offer counts too (the log line's route key is `not-ported`): a caller using such an endpoint keeps it firing |
| `<DEPLOYMENT_NAME>-unhealthy-targets` | any target group of the load balancer keeps an unhealthy target for five minutes | the pods that are not Ready (`kubectl -n velt get pods`, then `kubectl describe pod`) |

Two signals have no alarm: pods that cannot be scheduled, and the cache's volume filling. Container Insights publishes
both as metrics when it is on (the alarms bring it), but the module sets no alarm on them — check them on a schedule,
or alarm on the Container Insights metrics yourself:

```bash
kubectl get pods -A --field-selector=status.phase=Pending      # pods the autoscaler could not place (at the ceiling, or out of quota)
kubectl -n velt exec statefulset/velt-portable-redis -- df -h /data   # the cache's volume; grow the PVC before it fills
```

### Backups and restore

RDS keeps automated backups for `rds_backup_retention_days` (7 in persistent unless set) and restores to any second in
that window; deleted attachments stay recoverable in the versioned bucket for `attachment_noncurrent_version_days`. The
Backup and Restore runbook has what each backup covers, the restore
procedures, and the rehearsal to run before going live.

# Webhook payload encryption: a fresh 32-byte key, never printed

## Troubleshooting (AWS)

| Symptom | Likely cause | Action |
|---|---|---|
| `kubectl run --rm -i …` prints nothing, or only `try pressing enter` | an attached run raced the short-lived container | run detached, `kubectl wait`, then `kubectl logs` (Phases 4.5–4.7 are written that way) |
| `no such file or directory: docker run …` (zsh) | the provision CLI's command was stored in a variable, which zsh does not word-split | the `pcli()` shell function in Phase 3.1 |
| the console refuses a second workspace: `cannot create a second live apiKey … until every existing apiKey has a valid identify config` | the first workspace was seeded without `--identify-config` | re-run the seed with `--identify-config` (idempotent), or set the first workspace's identify configuration in the console |
| the seed refuses: `refusing to seed an invalid identify config: requireAutoOrgUser must be a boolean` (or `requireJwtToken`) | the identify configuration lacks one of its two flags | the Phase 4.7 value, which sets both |
| `no such file or directory: terraform -chdir=… output -raw` (zsh), or a secret whose DSN has an empty host | a command stored in a variable: zsh does not word-split it, and the value came out empty | the `tfo()` function (1.5); delete the empty secrets and the storage class, then redo 3.3 and 3.4 |
| `oras pull` or `cosign verify` → `error getting credentials` | your Docker configuration sends the release registry to a credential helper that fails; the registry needs no login | the empty `DOCKER_CONFIG` in Phase 0.1 (after its `DOCKER_HOST` line), with the ECR logins of 2.1 after it |
| `docker login` or the provision CLI → `failed to connect to the docker API` / `Cannot connect to the Docker daemon at unix:///var/run/docker.sock` | the empty `DOCKER_CONFIG` hid the docker CLI's context (Colima, Docker Desktop) | set `DOCKER_HOST` to your engine's socket (`docker context inspect` with your normal configuration prints it) — the line before `DOCKER_CONFIG` in 0.1 |
| `terraform apply` stops with `failed to refresh cached credentials … CreateOAuth2Token … The provided authorization grant is invalid` | Terraform's own refresh of an `aws login` / SSO session failed | do NOT plan and apply again yet: untaint what AWS shows healthy, re-plan to "0 to destroy" (1.3); then use the `credential_process` profile (0.3) |
| `helm install aws-load-balancer-controller` → `error validating data: the server is currently unable to handle the request` | the API server answers `/openapi/v2` in protobuf with 503 (seen on EKS 1.36; JSON and `/openapi/v3` answer 200), and Helm's client-side validation of the chart's `kind: List` asks for it | confirm: `kubectl proxy --port 8001 &` then `curl -s -o /dev/null -w '%{http_code}\n' -H 'Accept: application/com.github.proto-openapi.spec.v2@v1.0+protobuf' http://127.0.0.1:8001/openapi/v2` → 503. Re-run THAT install with `--disable-openapi-validation` (the API server still validates every object it applies); do not add the flag anywhere else.
````
